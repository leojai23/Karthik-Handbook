● Basic

What Is Arduino

Hardware

Arduino is a microcontroller board and its accompanying toolchain: a single chip running one program, with no operating system, no multitasking, and no filesystem — power it on and it runs your code, forever, from a fixed address, every time. This is the key structural difference from the Raspberry Pi tutorial in this Handbook: a Pi boots an OS and can run many programs at once with no real timing guarantee between them; an Arduino runs exactly one program with nothing else competing for the CPU, which is precisely why it's the more predictable (though far less capable) choice for tight, repetitive timing tasks.

The classic board, and the one this tutorial centres on, is the Uno (ATmega328P, 16MHz, 5V logic) — simple, well-documented, and the reference point almost every tutorial and library assumes unless stated otherwise.

Board Anatomy & Power

Hardware

An Uno can be powered three ways: the USB connector (5V, also used for programming and the Serial Monitor), the barrel jack (7–12V recommended, regulated down on-board to 5V), or the Vin pin directly. All digital and analog I/O pins run at 5V logic — the opposite of the Raspberry Pi's 3.3V-only GPIO, and the reason a sensor built for one platform sometimes needs a level shifter to safely talk to the other (see the Raspberry Pi tutorial's Level-Shift Calculator for that exact conversion in the 5V→3.3V direction).

The Sketch: setup() & loop()

Sketch

Every Arduino program ("sketch") has exactly two required functions:

void setup() {
  // runs once, at power-on or reset
  pinMode(13, OUTPUT);
  Serial.begin(9600);
}

void loop() {
  // runs forever, back-to-back, as fast as the code allows
  digitalWrite(13, HIGH);
  delay(500);
  digitalWrite(13, LOW);
  delay(500);
}

Digital I/O

Hardware

Three functions cover basic digital I/O: pinMode(pin, INPUT/OUTPUT) configures a pin's direction, digitalWrite(pin, HIGH/LOW) drives an output pin, and digitalRead(pin) reads an input pin's state. Every digital pin can source or sink up to 20mA recommended, 40mA absolute maximum — and the total across all I/O pins combined is capped at 200mA absolute maximum. Both figures are meaningfully higher than the Raspberry Pi's roughly 16mA-per-pin/50mA-total guideline, one of the practical reasons Arduino can sometimes drive a small load (a single LED at full brightness, a small piezo buzzer) directly where a Pi would need a transistor stage regardless.

Analog Input: analogRead()

Hardware

Unlike the Raspberry Pi — which, as covered in its own tutorial, has no built-in ADC at all — an Arduino Uno has six dedicated analog input pins (A0–A5) wired to a genuine on-chip 10-bit ADC. analogRead(pin) returns an integer from 0 to 1023, mapping linearly against the reference voltage (5V by default):

voltage = analogRead(A0) / 1023.0 * 5.0;

Worked example: analogRead() returns 614 → 614/1023 × 5 = 3.00V. Verify it, and the ADC's step size, in the calculator above.

Analog Output: PWM & analogWrite()

Hardware

The Uno has no true DAC either — "analog output" is actually PWM on six marked pins (3, 5, 6, 9, 10, 11, driven by three of the chip's internal timers), producing a fast on/off square wave whose average value mimics an analog level. analogWrite(pin, value) takes an 8-bit value, 0–255, directly setting that duty cycle — the same PWM concept, and the same averaging-by-switching-fast principle, as the PWM sections of both the PLC Learning and VFD tutorials, just at a much smaller scale.

Worked example: analogWrite(pin, 191) gives a duty cycle of 191/255 × 100 ≈ 74.9% — roughly three-quarters brightness on an LED, or three-quarters speed on a small DC motor driven through an appropriate driver circuit.

Serial Monitor & Debugging

Sketch

With no screen or OS to print to, Serial.begin(baud) plus Serial.print()/Serial.println() is the primary debugging tool — text sent over the same USB connection used to upload the sketch, read live in the IDE's Serial Monitor. Matching the baud rate on both ends (sketch and monitor) is essential; a mismatch shows up as garbled text rather than a clean error.

Pull-Ups & Debouncing

Hardware

Exactly the same floating-input problem from the Raspberry Pi tutorial applies here: a button with nothing else connected reads unpredictably when open. pinMode(pin, INPUT_PULLUP) enables the chip's internal pull-up resistor in software, with no extra wiring — the pin reads HIGH when open, LOW when the button pulls it to ground.

A second, mechanical problem: a physical switch's contacts don't close cleanly — they bounce, producing several rapid open/close transitions over a few milliseconds that a fast-reading microcontroller sees as multiple presses. The simple fix is a short software delay after detecting a change (tens of milliseconds) before trusting the new state as stable; more advanced sketches track the time of the last change and only accept a new state once enough time has passed since the last transition.

Interrupts

Sketch

Polling a pin inside loop() only notices a change whenever that line of code happens to run next — fine for a button, too slow for something that must be caught within microseconds (a fast-pulsing encoder, a precise timing reference). attachInterrupt() instead registers a function that the chip calls immediately when a specified pin changes, interrupting whatever loop() was doing at that exact moment.

Interrupt handlers should be kept extremely short — no delay(), minimal logic, usually just setting a flag or incrementing a counter for loop() to act on afterward — since nothing else on the chip, including other interrupts on most boards, can run until the handler returns.

Timers: millis() vs delay()

Sketch

delay(ms) blocks everything — literally nothing else in loop() runs until it returns, exactly the stall warned about in the setup/loop diagram above. millis() instead returns the number of milliseconds since the sketch started, letting the program check elapsed time without blocking:

unsigned long lastBlink = 0;
void loop() {
  if (millis() - lastBlink >= 500) {
    lastBlink = millis();
    digitalWrite(13, !digitalRead(13));  // toggle
  }
  // ...other code keeps running every pass, unblocked...
}

This pattern — "non-blocking timing" — is the standard way to do several timed things at once on a single-threaded chip with no OS scheduler to share time for you.

I2C & SPI on Arduino

Hardware

The Uno exposes both buses on fixed pins: I2C on A4 (SDA) / A5 (SCL), SPI on digital pins 11 (MOSI), 12 (MISO), 13 (SCK) plus a chosen chip-select pin — different physical pins from the Raspberry Pi's assignments covered in its own tutorial, though the underlying protocols (and the Wire and SPI libraries wrapping them) work the same way conceptually on both platforms.

Driving Motors & Relays

Hardware

Even at the Uno's higher 20–40mA-per-pin budget, that's still nowhere near enough to drive a relay coil, solenoid, or motor directly. The same pattern from the Electronics & Instrumentation tutorial applies unchanged: a GPIO pin switches a transistor or MOSFET, which switches the actual load current from a separate, appropriately-rated supply — or, more commonly in practice, a ready-made relay or motor driver module that packages that transistor stage (and usually opto-isolation) onto one small board.

Libraries & the Ecosystem

Sketch

Most practical Arduino work leans on libraries rather than raw register manipulation: Servo for RC servos (abstracting away the exact 1–2ms pulse-width math from the Raspberry Pi tutorial's servo section into a simple myServo.write(angle) call), Wire for I2C, SPI for SPI, and a vast third-party library ecosystem for specific sensors and modules, installable directly through the IDE's Library Manager. Reading a library's example sketches first is usually faster than reading its source — most document their intended usage clearly through working examples.

Arduino as a Modbus Device

Sketch

With a cheap RS-485 transceiver module (or a direct USB-serial connection for Modbus TCP-over-a-gateway setups), an Arduino can act as either side of a Modbus conversation covered in this Handbook's Modbus tutorial: most commonly as a slave — the field device itself, exposing its sensor readings and relay states as registers/coils for a PLC or a Raspberry Pi master (see that tutorial's Python examples) to poll — using a library like ModbusRTUSlave to handle the frame parsing, CRC, and register mapping so the sketch itself only needs to update plain variables.

This is a natural division of labour across this Handbook's subjects: Arduino as the cheap, deterministic field-level sensor/actuator node; a Raspberry Pi or PLC as the master polling several of them over one RS-485 bus.

Memory Constraints

Hardware

An Uno has just 32KB of flash (program storage), 2KB of SRAM (variables, at runtime), and 1KB of EEPROM (small amounts of data that must survive a power cycle) — thousands of times less than even the smallest Raspberry Pi. This isn't a minor inconvenience: a handful of String objects doing repeated concatenation, or one oversized array, can exhaust 2KB of SRAM and cause silent, hard-to-diagnose crashes or corrupted data with no error message at all, since there's no OS underneath to catch the fault gracefully. Prefer fixed-size character arrays over String in memory-tight sketches, and watch flash usage (reported after every compile) as a program grows.

Watchdog Timer & Reliability

Hardware

The chip includes a hardware watchdog timer that resets the whole board if not periodically "fed" (acknowledged) by the running sketch — a safety net against a sketch hanging in an infinite loop or an unresponsive state with no human around to power-cycle it. Enabling it and remembering to feed it inside loop() is standard practice for anything deployed unattended, the same reliability goal the Raspberry Pi tutorial's systemd auto-restart section serves at the OS level instead.

Power Management & Sleep Modes

Hardware

For battery-powered projects, the chip's various sleep modes can cut active current draw from tens of milliatts down to microamps between readings — waking periodically (via a timer interrupt) or on an external event (a button press, a sensor interrupt) to take a reading and go straight back to sleep. This is the kind of optimisation that matters enormously for a coin-cell sensor meant to run for months, and essentially never matters for a USB-powered or mains-powered project — know which category a given build falls into before spending time on it.

Beyond the Uno

Hardware

The Uno is the reference board, but the same core concepts (setup/loop, digital/analog I/O, PWM, interrupts) carry over to the wider family: the Mega (more I/O pins, more memory, same 5V/16MHz core), the Nano (same chip, smaller footprint), and increasingly common third-party boards like the ESP32 (WiFi/Bluetooth built in, 3.3V logic like the Pi rather than 5V, far more memory and clock speed) programmable through the same Arduino IDE and largely the same API, blurring the line between "simple microcontroller" and "small networked computer" that this whole tutorial otherwise draws fairly sharply.

Basic Size an LED resistor on Arduino's 5V rail

A red LED (Vf = 1.8V) is driven at 15mA from an Arduino digital pin's 5V output. What resistor value is needed?

Answer R = (5 − 1.8) / 0.015 = 3.2/0.015 = 213.3Ω. Round up to a standard value (220Ω). Compare this to the Raspberry Pi tutorial's version of the same calculation at 3.3V — a materially different resistor for the same LED and current.
Basic Convert an ADC reading to a voltage

analogRead(A0) returns 614. What voltage does that represent, assuming the default 5V reference?

Answer 614 / 1023 × 5 = 3.00V.
Intermediate Find a PWM duty cycle from an analogWrite value

analogWrite(9, 191) is called. What duty cycle does this produce?

Answer 191 / 255 × 100 ≈ 74.9%.
Intermediate Compute a byte's transmission time at a given baud rate

At 9600 baud with standard 8N1 framing (10 bits per byte including start/stop), how long does it take to transmit one byte?

Answer Bit time = 1,000,000 / 9600 ≈ 104.17µs. Byte time = 104.17 × 10 ≈ 1041.7µs ≈ 1.04ms. This exact framing math is also what sets the Modbus RTU tutorial's 3.5-character inter-frame silence timing.
Advanced Diagnose a memory-related crash

A sketch that builds up long text messages using repeated String concatenation runs fine for a while, then starts behaving erratically with no compiler error and no obvious cause. What's the likely root cause, and what's the standard fix?

Answer Likely SRAM exhaustion/fragmentation from repeated dynamic String allocation on a chip with only 2KB of SRAM and no OS-level memory protection to catch it cleanly — it just silently corrupts. Standard fix: avoid repeated String concatenation in long-running code; use fixed-size character arrays and functions like snprintf() instead.
Advanced Choose the right controller for a mixed automation task

A small project needs: (1) a sensor node out at a remote tank reporting level every few seconds over RS-485, (2) a central point logging all the readings and serving a web dashboard, and (3) a guaranteed-safe emergency shutoff if the tank level is critically high. Which controller from the Arduino/Raspberry Pi/PLC comparison table fits each role, and why?

Answer (1) Arduino — cheap, simple, perfectly adequate for reading one sensor and reporting it as a Modbus slave periodically. (2) Raspberry Pi — needs real compute, storage, and networking for logging and a web dashboard, none of which Arduino can do and none of which needs PLC-grade determinism. (3) PLC (with certified safety I/O) — the only one of the three actually rated for a safety-critical shutoff function, exactly as the PLC tutorial's Safety Interlocking section and this tutorial's comparison table both emphasise.
