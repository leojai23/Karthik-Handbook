● Basic

Why Industrial Ethernet

OT

The Modbus tutorial in this Handbook covers RS-485 serial and Modbus TCP in depth — simple, well-understood, still enormously common. Industrial Ethernet protocols (EtherNet/IP, PROFINET) exist for what Modbus TCP wasn't designed for: hard real-time motion coordination across many devices, richer device description and auto-configuration, and native integration with the standard IT networking equipment (switches, routers, firewalls) that the rest of a modern facility already runs on.

Ethernet Fundamentals for OT

IT

A few IT concepts an OT-focused reader benefits from pinning down: a switch forwards each frame only to the port its destination lives on (unlike an old-style hub, which repeated everything to every port), giving each device effectively its own full-duplex (simultaneous send/receive) link rather than a shared, collision-prone one. This switching behaviour is a prerequisite for the deterministic timing that PROFINET IRT and EtherNet/IP's cyclic I/O depend on — a shared, collision-based network simply cannot guarantee the sub-millisecond delivery those modes promise.

Managed Switches & VLANs

IT

An unmanaged switch just forwards traffic; a managed switch adds configuration, monitoring, and — most importantly for OT — VLANs (Virtual LANs), which split one physical switch into multiple logically separate networks. Putting the PLC/drive network on one VLAN and the HMI/historian network on another, for instance, keeps broadcast traffic and faults contained to the segment that generates them, and lets a firewall or router control exactly what crosses between segments — the practical mechanism that makes the Purdue model's level separation real rather than just a diagram.

IP Addressing for OT Networks

IT

OT devices are overwhelmingly given static IP addresses rather than DHCP — a PLC or drive that's unreachable because a DHCP lease expired or renewed to a different address is a production-stopping problem in a way it rarely is for an office laptop. Common practice is a documented, consistent addressing scheme per cell or line (e.g. every device on Line 3 lives in 10.3.x.x), making a device's network location predictable from its physical location — invaluable during troubleshooting, and the exact kind of planning the Subnet Calculator above supports.

EtherNet/IP & CIP

OT

EtherNet/IP (the "IP" stands for Industrial Protocol, not Internet Protocol, despite running over standard Ethernet/IP networking) carries CIP, the Common Industrial Protocol, using two distinct messaging modes over two different ports:

Every CIP connection follows this same two-phase shape: negotiate and open with explicit TCP messaging, then stream with implicit UDP messaging for as long as the connection stays open — a direct parallel to how the Modbus tutorial's RTU frames separate addressing/setup from the actual cyclic polling a master performs.

PROFINET

OT

PROFINET offers two real-time classes with very different hardware demands:

ClassTypical cycle timeRequires
RT (Real-Time)1–10msstandard managed Ethernet switches
IRT (Isochronous Real-Time)sub-millisecond, down to ~250µs (some extensions to ~31µs)PROFINET-certified switches with hardware-synchronised time slots

IRT's extreme determinism (jitter below 1 microsecond) is what multi-axis motion control and tightly coordinated drive synchronisation need — the kind of application where even RT's 1–10ms isn't tight enough. Devices describe their capabilities and configuration options to engineering software through a GSD file (GSDML format, XML-based) — the PROFINET equivalent of the register maps covered in the Modbus tutorial, but machine-readable and auto-loadable rather than something an engineer manually transcribes from a datasheet.

Modbus TCP: Where It Still Fits

OT

None of this displaces Modbus TCP, covered fully in the Modbus tutorial — it remains the simplest, most universally supported option for straightforward data exchange (reading a sensor, writing a setpoint) where hard real-time motion coordination isn't the requirement. A practical rule of thumb: Modbus TCP for simple point-to-point or gateway integration, EtherNet/IP or PROFINET where many coordinated devices need guaranteed, tight cyclic timing, and OPC UA (Advanced, below) wherever the data needs to cross cleanly into IT systems with real security.

Network Redundancy

IT

A single switch or cable failure taking down an entire production line's network is unacceptable in most facilities, so OT networks commonly use ring topologies with a redundancy protocol (RSTP — Rapid Spanning Tree Protocol, or PROFINET's own MRP — Media Redundancy Protocol) that detects a break in the ring and reroutes traffic the other way around it, typically within tens to low hundreds of milliseconds — fast enough that most control systems never notice the brief interruption.

Diagnosing Network Issues in the Field

OT

Before suspecting the application layer (a PLC program, a SCADA tag), rule out the network itself: ping confirms basic reachability; a managed switch's port statistics (error counters, collision counts, link speed/duplex) reveal a failing cable or a mismatched duplex setting long before the symptom shows up as a flaky PLC connection; and physically checking link LEDs on both ends of a suspect cable catches the simplest failures (unseated connector, damaged cable) in seconds. Many "intermittent PLC communication fault" tickets turn out to be a marginal cable or a switch port set to the wrong speed/duplex, not a logic problem at all.

● Advanced

OPC UA: the IT/OT Bridge

IT

OPC UA (Unified Architecture, default port 4840) solves a problem none of the other protocols in this tutorial were built for: letting OT data reach IT and cloud systems in a structured, self-describing, secure way. It supports two communication patterns — the original client/server model (a client requests data or calls a method on a server, much like the Modbus tutorial's master/slave polling) and a newer publish/subscribe model (the same decoupled pattern the ESP32 & IoT tutorial covers for MQTT) — both built on the same underlying information model: data isn't just a raw register number, it's a named, typed node with units, a description, and relationships to other nodes, all discoverable by a generic client with no vendor-specific documentation required.

This self-describing structure is the key practical difference from Modbus: a Modbus master has to already know that register 40012 means "Tank 3 Level in Litres" from a datasheet; an OPC UA client can ask the server and get that answer back directly.

OPC UA Security

IT

Security is built into the OPC UA specification itself, not bolted on afterward: certificate-based authentication identifies clients and servers to each other, and messages can be signed (tamper-evident) and encrypted (confidential) at the protocol level. This is a sharp contrast with the historical reality of Modbus, EtherNet/IP, and PROFINET, none of which were designed with authentication or encryption in mind — a gap the Network Security for OT section below addresses with network-level controls instead, precisely because those protocols can't defend themselves.

Choosing a Protocol

IT
NeedReasonable choice
Simple, cheap, well-understood point-to-point or gateway linkModbus RTU/TCP
Many coordinated devices, tight but not extreme cyclic timingEtherNet/IP
Multi-axis motion control, sub-millisecond determinismPROFINET IRT
Structured, secure data exchange up into IT/cloud/SCADAOPC UA
Lightweight wireless telemetry to a cloud dashboardMQTT (see the ESP32 & IoT tutorial)

These aren't mutually exclusive — a real site very often runs several of these at once, each at the layer it fits: PROFINET or EtherNet/IP down at the machine level, OPC UA carrying that data up to a historian or MES, and Modbus TCP gluing in a simpler device that never got a native driver for whatever the newer protocols demand.

Extending the Gateway: OPC UA to the Cloud

IT

The ESP32 & IoT tutorial's gateway example bridges a wired Modbus RS-485 network to an MQTT broker. The same shape works with OPC UA on the upstream side instead: a gateway device (often a small industrial PC or a Raspberry Pi, as covered in its own tutorial, rather than an ESP32 — OPC UA's security and information-model overhead generally wants more horsepower than a microcontroller comfortably offers) polls Modbus, PROFINET, or EtherNet/IP devices on the OT side, and exposes that same data as a proper OPC UA server on the IT side — letting any standard OPC UA client (a SCADA system, a cloud connector, a historian) consume it without ever needing to speak the original field protocol directly.

Network Security for OT

IT

Because most OT protocols have no built-in security, the defence has to live in the network itself: strict segmentation along Purdue model lines (nothing below the DMZ ever talks directly to anything above it), firewalls at the DMZ controlling exactly which traffic is allowed to cross, and VLANs keeping even OT-to-OT traffic contained to the cells that need it. Patching is also a harder problem in OT than IT — a PLC or drive often can't be patched or rebooted without stopping production, so compensating network-level controls matter even more here than in a typical office IT environment where patching on a regular cadence is the default expectation.

Time Synchronization: IEEE 1588 PTP

OT

PROFINET IRT's sub-millisecond determinism depends on every device on the network sharing a common, precisely synchronised sense of time — provided by IEEE 1588 Precision Time Protocol (PTP), which synchronises clocks across a network to sub-microsecond accuracy using specialised hardware timestamping in the switches themselves (ordinary NTP, by contrast, is only accurate to milliseconds, nowhere near tight enough). This is the same underlying need for tight, deterministic timing that motivated the PLC Learning tutorial's scan-cycle discussion and the VFD tutorial's coordinated-drive scenarios — just solved at the network layer instead of inside a single controller.

● Practice Exercises
Basic Calculate a subnet's usable host range

A device is configured with IP 10.10.5.0/28. What's the network address, broadcast address, and usable host range?

Answer Network: 10.10.5.0. Broadcast: 10.10.5.15. Usable range: 10.10.5.1 through 10.10.5.14 (14 usable hosts). Confirm it in the Subnet Calculator above.
Basic Place a device on the Purdue model

An MES system that collects production data from several PLCs and feeds a plant historian — which Purdue level does it belong to, and what should it never connect to directly?

Answer Level 3 (site operations). It should never connect directly to Level 4/5 business systems (ERP, corporate network, internet) — any data headed that direction must pass through the DMZ.
Intermediate Estimate network load for a cyclic I/O network

50 EtherNet/IP devices each send a 64-byte update every 10ms. Roughly what bandwidth does that consume, and is a 100Mbit network adequate?

Answer 50 × 64 × 8 × (1000/10) = 2,560,000 bps ≈ 2.56Mbps — comfortably within a 100Mbit link, with enormous headroom to spare. Confirm it in the Network Load Estimator above.
Intermediate Identify EtherNet/IP's two messaging phases

An EtherNet/IP connection is being established between a PLC and a drive. What happens first, over which port/protocol, and what happens once that's done?

Answer First, explicit messaging over TCP port 44818 performs a Forward_Open handshake to negotiate and establish the connection. Once established, implicit messaging over UDP port 2222 carries the ongoing cyclic I/O data on a fixed schedule for as long as the connection stays open.
Advanced Choose the right real-time class for a motion application

A packaging machine needs multiple servo axes coordinated to within a few hundred microseconds of each other. Which PROFINET class is required, and what hardware does it demand that plain RT doesn't?

Answer IRT (Isochronous Real-Time) — plain RT's 1–10ms cycle times aren't tight enough for sub-millisecond axis coordination. IRT requires PROFINET-certified switches with hardware-synchronised time slots (built on IEEE 1588 PTP), not just any standard managed switch.
Advanced Explain OPC UA's key advantage over Modbus for IT integration

A company wants plant-floor data (currently on Modbus TCP) available to a cloud analytics platform, with proper authentication and encryption. Why is OPC UA, rather than extending Modbus TCP further, the more natural fit for the IT-facing side of this project?

Answer Two reasons: OPC UA has security built into the protocol itself (certificate-based authentication, signed/encrypted messages), where Modbus has none at all and would need to be wrapped in external security entirely; and OPC UA's self-describing information model means a generic client can discover what a data point represents (name, units, type) without needing a separately maintained register-map document, unlike a raw Modbus register number.
