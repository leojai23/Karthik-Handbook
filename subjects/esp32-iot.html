Wireless Microcontroller & IoT Tutorial

ESP32 & IoT

A guided path from GPIO and the built-in ADC through WiFi and MQTT, into building an actual IoT gateway that bridges wired field devices to the cloud. Copper-tagged sections are hardware/electrical; teal-tagged sections are networking/software.

ADC Reading → Voltage (12-bit)

The ESP32's built-in ADC is 12-bit (0–4095), against a nominal 3.3V reference: voltage = raw / 4095 × V_ref.

LEDC PWM Duty Cycle

Unlike Arduino's fixed 8-bit analogWrite(), the ESP32's LEDC peripheral lets you choose the resolution: duty% = value / (2resolution−1) × 100.

Deep Sleep Battery Life Estimator

A duty-cycled sensor node spends most of its life asleep at a few microamps, briefly waking to take a reading and transmit. Average current, weighted by time in each state, determines battery life.

MQTT Data Volume Estimator

Useful for sizing a cellular/metered connection: bytes/day = (payload ÷ interval) × 86400.

● Basic

What Is an ESP32

Hardware

The ESP32 is a dual-core microcontroller with WiFi and Bluetooth built directly into the chip — no separate shield or module needed, unlike adding WiFi to a classic Arduino. It's commonly programmed through the Arduino IDE (via an add-on board package) using the same setup()/loop() shape from the Arduino Concepts tutorial, which makes it an easy next step — but underneath, that similarity hides an important difference covered properly in FreeRTOS Tasks below: an ESP32 sketch is not the only thing running, the way a classic Uno sketch is.

It occupies a distinct niche from both other controllers in this Handbook: more capable and wireless-native compared to a classic Arduino, but still a single-purpose embedded device rather than a full OS-driven computer like the Raspberry Pi.

GPIO on the ESP32

Hardware

ESP32 GPIO runs at 3.3V logic — like the Raspberry Pi, unlike the Arduino Uno's 5V, so a 5V sensor still needs the same level-shifting treatment from the Raspberry Pi tutorial before connecting it here. Two further wrinkles specific to this chip:

  • Strapping pins (commonly GPIO0, 2, 12, 15) have a special role at boot time — they're sampled to decide the boot mode, so anything wired to them that holds a pin in the "wrong" state at power-up can prevent the board from booting at all. Avoid using these for anything that might be driven low by external hardware at power-on.
  • Input-only pins (GPIO34–39) have no internal pull-up/pull-down and cannot be used as outputs — fine for reading sensors, unusable for driving an LED or anything else.

Current limits are broadly similar in spirit to the other boards in this Handbook (tens of mA per pin, never enough to drive a relay or motor directly) — the same transistor/driver-module pattern from the Electronics and Arduino tutorials applies unchanged.

Powering & Boot Gotchas

Hardware
A very common "random reset" cause WiFi transmission draws brief current spikes of several hundred milliamps. A USB cable or power source that can't supply that spike cleanly causes a brownout — the chip resets, often repeatedly, right as it tries to connect to WiFi. If a board resets specifically when WiFi activity starts, suspect the power supply and cable before suspecting the code.

A decent USB cable and a power source rated for at least 500mA–1A resolves the great majority of these otherwise confusing, intermittent reset issues.

The 12-Bit ADC & Its Quirks

Hardware

The ESP32's built-in ADC is 12-bit (0–4095) — finer resolution than the Arduino Uno's 10-bit ADC, and unlike the Raspberry Pi, which (as its own tutorial covers) has no built-in ADC at all. At a 3.3V reference, that works out to about 3.3V/4095 ≈ 0.806mV per step — the exact same resolution figure already verified in the Electronics & Instrumentation tutorial's ADC section for a generic 12-bit/3.3V system.

Two documented quirks worth knowing before debugging a "why is my analog reading garbage" problem: the ADC has known nonlinearity near 0V and near the reference voltage (Espressif provides calibration APIs to compensate), and — more operationally important — ADC2's pins conflict with WiFi on the original ESP32: once the WiFi driver is running, ADC2 readings become unreliable or fail outright. The fix is simple: use ADC1 (GPIOs 32–39) for any analog sensor on a WiFi-connected project, and reserve ADC2 pins for projects that never enable WiFi.

Arduino IDE on the ESP32

Software

Installing the ESP32 board package (via the IDE's Boards Manager) brings the same sketch structure, library ecosystem, and upload workflow from the Arduino Concepts tutorial to this chip — pinMode(), digitalWrite(), analogRead() all still work, now joined by WiFi- and Bluetooth-specific libraries (WiFi.h, BluetoothSerial.h) that have no equivalent on a plain Uno.

WiFi Basics: STA & AP Modes

Software

An ESP32 can join an existing network as a client — Station (STA) mode, the common case for a sensor reporting to a home or site network — or create its own network for other devices to join directly — Access Point (AP) mode, useful for initial configuration (a phone connects directly to the ESP32 to enter WiFi credentials) or for a small standalone network with no existing infrastructure. Some projects use both: AP mode briefly for first-time setup, then STA mode for normal operation afterward.

Connecting to WiFi

Software
#include <WiFi.h>

void setup() {
  Serial.begin(115200);
  WiFi.begin("ssid", "password");
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.println(WiFi.localIP());
}

The blocking while loop here is fine at startup (nothing else needs to happen until the network is up), but the same non-blocking-timing discipline from the Arduino Concepts tutorial's millis() section applies once the sketch is doing other things concurrently with maintaining a connection.

HTTP Requests: ESP32 as a Client

Software

With WiFi connected, the HTTPClient library lets a sketch make outbound HTTP requests directly — posting a sensor reading to a cloud API or a local server with just a handful of lines, no separate gateway device required. This is the most common pattern for a simple "read a sensor, send the value somewhere" project that doesn't need the richer pub/sub model of MQTT (see Advanced below).

Hosting a Web Server

Software

The reverse direction also works: an ESP32 can run its own lightweight web server (via WebServer.h or the more capable ESPAsyncWebServer library), serving a simple status page or accepting commands over HTTP from any browser on the network — a small-scale version of the Flask dashboard pattern from the Raspberry Pi tutorial, running directly on the microcontroller with no separate computer needed.

PWM via LEDC

Hardware

Where the Arduino Uno's analogWrite() is fixed at 8-bit resolution on a handful of pins, the ESP32's LEDC peripheral is configurable — choose the resolution (up to 16-bit, though frequency and resolution trade off against each other) and frequency per channel, and assign it to almost any GPIO pin rather than a fixed set. Worked example: at 10-bit resolution, a duty value of 750 gives 750/1023 × 100 ≈ 73.3% — confirm it, and other resolutions, in the calculator above.

Deep Sleep & Power Management

Hardware

For battery-powered sensor nodes, deep sleep is what makes months of battery life realistic: current draw drops to roughly 10–150µA depending on the wake source configured, versus tens of milliamps while active and transmitting. The chip can wake on a timer, or on a change at specific RTC GPIO pins (0, 2, 4, 12–15, 25–27, 32–39) — not every GPIO pin can trigger a wake-up, only this subset wired to the always-on RTC domain that stays powered through deep sleep.

Worked example: a node waking every 60s, active for 0.2s at 80mA, sleeping the rest of the time at 10µA, averages roughly 0.277mA — a 2000mAh battery would last about 301 days. Try other duty cycles in the calculator above; the relationship is highly non-linear, so even small reductions in active time or wake frequency extend battery life dramatically.

OTA Updates

Software

Over-The-Air updates let a new sketch be uploaded over WiFi instead of a USB cable — essential once a device is deployed somewhere physically inconvenient to reach (inside an enclosure, up on a pole, across a site). The ArduinoOTA library handles the common case; production fleets typically go further with a dedicated OTA update server that can track which devices are on which firmware version and roll updates out in a controlled way rather than all at once.

MQTT: the Pub/Sub Pattern

Software

MQTT is the dominant lightweight IoT messaging protocol, built around publish/subscribe rather than direct device-to-device requests: a device publishes a message to a named topic (e.g. site1/tank3/level) on a central broker; any number of other devices or applications subscribed to that topic receive the message, with neither side needing to know who (or how many) is on the other end.

MQTT also defines three Quality of Service levels: QoS 0 (fire-and-forget, no delivery guarantee), QoS 1 (guaranteed delivery, possible duplicates), and QoS 2 (guaranteed exactly-once delivery, at the cost of more protocol overhead) — chosen per message based on how much a dropped or duplicated reading actually matters for that particular data.

Building an IoT Gateway: ESP32 + Modbus + MQTT

Software

A particularly useful role for an ESP32 in this Handbook's wider context: bridging a wired Modbus RS-485 network of field devices — exactly the relay boards and transmitters covered in the Modbus tutorial — onto WiFi/MQTT, without needing a full Raspberry Pi on-site.

FreeRTOS Tasks & Multitasking

Software

Here's the detail glossed over earlier: an ESP32 running an Arduino-style sketch is not single-program-no-OS the way a classic Uno is. Underneath, it's running FreeRTOS, a real-time operating system, with the sketch's own setup()/loop() running as just one task among others — the WiFi and Bluetooth stacks run as separate tasks, often pinned to the chip's second core, which is exactly why a WiFi connection can keep working even while loop() is busy with something else (a real practical difference from the Arduino tutorial's warning that a blocking delay() stalls everything).

Advanced sketches can create their own additional FreeRTOS tasks directly (xTaskCreate()), assign them to a specific core, and coordinate between them with queues or semaphores — genuine concurrent programming, not available at all on a classic single-core, no-OS Arduino Uno.

Security Basics for IoT Devices

Software

The same discipline from the Raspberry Pi tutorial's Remote Access & Security section applies here, with IoT-specific sharp edges: never hardcode WiFi or MQTT credentials into a sketch that might end up shared or published (use a separate config file, excluded from version control); use WPA2/WPA3 for the WiFi network itself; and use TLS for the MQTT connection wherever the broker is reachable outside a trusted local network, since plain MQTT sends topics and payloads unencrypted. Mass-produced IoT devices shipped with default, unchangeable credentials are the textbook cause of large botnets built entirely from compromised smart devices — a cautionary case for why "it's just a sensor" is not a reason to skip basic security hygiene.

● Practice Exercises
Basic Convert a 12-bit ADC reading to a voltage

An ESP32's analogRead() returns 2800 on a 3.3V reference. What voltage does that represent?

Answer 2800 / 4095 × 3.3 ≈ 2.256V.
Basic Pick the right ADC unit for a WiFi-connected sensor

A project reads an analog sensor while also maintaining a WiFi connection. Which ADC unit should the sensor be wired to, and why?

Answer ADC1 (GPIOs 32–39). ADC2's pins conflict with the WiFi driver on the original ESP32 — once WiFi is running, ADC2 readings become unreliable or fail. ADC1 has no such conflict.
Intermediate Compute an LEDC duty cycle

An LEDC channel is configured for 10-bit resolution, and the duty value is set to 750. What's the resulting duty cycle percentage?

Answer 750 / 1023 × 100 ≈ 73.3%.
Intermediate Estimate battery life for a sensor node

A 2000mAh battery powers a node that wakes every 60s, stays active for 0.2s at 80mA, and sleeps the rest of the time at 0.01mA. Roughly how many days will it run?

Answer Average current ≈ (0.2/60)×80 + (59.8/60)×0.01 ≈ 0.277mA. Battery life ≈ 2000/0.277 ≈ 7230 hours ≈ 301 days. Confirm it in the calculator above.
Advanced Estimate MQTT data volume for connectivity planning

A device publishes a 120-byte payload every 30 seconds. Roughly how much data does that generate per day?

Answer (120/30) × 86400 = 345,600 bytes/day ≈ 337.5 KB/day — roughly 9.9MB/month, small enough to be comfortable even on a constrained cellular IoT data plan.
Advanced Explain why ESP32 WiFi survives a blocking loop() the way Arduino can't

On a classic Arduino Uno, a long delay() inside loop() stalls everything, including any communication. On an ESP32, a WiFi connection can often survive a similarly blocking stretch of code in loop(). Why?

Answer Because the ESP32 runs FreeRTOS underneath the Arduino-style sketch: the WiFi (and Bluetooth) stack runs as its own separate task, typically on the second core, independent of whatever the sketch's own setup()/loop() task is doing. A classic Uno has no OS and no second task to pick up the slack — loop() truly is the only thing happening.
