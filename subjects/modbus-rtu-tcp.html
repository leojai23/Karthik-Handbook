Field Troubleshooting Checklist

Work down the relevant list in order — each step rules something out before you move to the next. Click a step to mark it checked as you go.

RTU

Slave Not Responding (Serial)

  • Is the slave powered on?

    Check for a power/status LED on the device, and verify supply voltage at its terminals.

  • Are the A/B (D+/D−) wires swapped?

    The single most common RS-485 fault. Swap them and retest if you're not certain they're correct.

  • Is the bus terminated correctly?

    120Ω resistors at the two physical ends of the bus only — missing termination or terminating every device both cause problems.

  • Is there a common ground/reference between devices?

    Especially important when devices have separate power supplies — a floating reference causes intermittent or garbled communication.

  • Do serial parameters match exactly?

    Baud rate, parity, data bits, and stop bits must match on both master and slave — a single mismatch (e.g. even vs. no parity) looks identical to a dead device.

  • Is the slave address correct?

    Check the device's configured ID (DIP switches or a config menu) against what your master is actually requesting.

  • Do both ends agree on RTU vs. ASCII mode?

    Mismatched framing mode produces line noise, not a clean error.

  • Run a Diagnostics loopback test (FC 0x08)

    If the device won't even echo a loopback request, the fault is physical-layer, not application-level. See the Diagnostic Function Code section above.

  • Retest with a known-good master tool

    Try ModScan, QModMaster, or modpoll instead of your own application, to rule out a bug in your code versus a device/wiring fault.

TCP

Slave Not Responding (Ethernet)

  • Can you ping the device's IP address?

    Confirms basic network reachability before even trying Modbus.

  • Is port 502 open?

    Check for a firewall (on either end, or a switch ACL) blocking TCP port 502 specifically, even though ping succeeds.

  • Is the Unit ID correct?

    If you're going through a gateway to RTU slaves behind it, the IP gets you to the gateway — the Unit ID still has to match the actual slave on the serial side.

  • Is something else already holding the connection?

    Many simple Modbus TCP slaves only accept one (or a small, fixed number of) concurrent connections — a second master, or a stale unclosed connection from a crashed client, can lock everyone else out.

  • Is it actually MBAP-framed TCP, or RTU-over-TCP?

    See RTU-over-TCP vs. Native Modbus TCP above — a cheap serial-to-Ethernet converter may be tunneling raw RTU bytes (with a CRC) rather than real MBAP framing.

● Basic

What Is Modbus?

Modbus is a messaging protocol for exchanging data between industrial devices — PLCs, sensors, drives, meters, HMIs. Modicon published it in 1979 for its own PLCs; because the specification was open and simple to implement, it became a de facto standard that outlived the company that created it. Today it's one of the most common protocols on factory floors, in building automation, and in power/utility systems.

Its popularity comes from being deliberately unambitious: a handful of data types, a small set of commands, and no vendor lock-in. A $10 sensor and a six-figure PLC can both speak it.

Master & Slave Roles

Modbus is strictly client-server (the original spec calls it master/slave). The master initiates every exchange — a slave never speaks unless spoken to. This keeps slave devices simple: they just listen for a request addressed to them and reply.

  • Master — usually a PLC, SCADA system, or HMI. Sends requests like "read holding registers 0–9 from device 5."
  • Slave — a field device (sensor, drive, meter). Responds only when its own address is in the request.

One master can talk to many slaves (up to 247 on an RTU bus); a slave only ever replies to the master that asked it something.

RTU vs TCP at a Glance

"Modbus" is really a shared data model and command set riding on two different transports. Same vocabulary, different wires.

The Data Model

Every Modbus slave exposes the same four kinds of data, regardless of transport. Think of them as four separate tables, each with its own address space 0–65535:

TypeSizeAccessTypical use
Coil1 bitRead/WriteA digital output — a relay, a motor-start command
Discrete Input1 bitRead-onlyA digital input — a limit switch, a door sensor
Holding Register16 bitsRead/WriteA setpoint, a configuration value
Input Register16 bitsRead-onlyA measured value — temperature, flow rate

Nothing in the protocol enforces what a register actually means — that mapping (register 40012 is "motor RPM," scaled by 10) is documented per device, usually in a PDF from the manufacturer.

Function Codes, Briefly

Every request carries a function code — a single byte saying what operation to perform. At the basic level, you only need the four you'll use constantly:

  • 0x03 — Read Holding Registers
  • 0x04 — Read Input Registers
  • 0x06 — Write Single Register
  • 0x05 — Write Single Coil

The full reference table with all standard codes is in the Intermediate section below.

RTU

RTU Frame Structure

An RTU frame has no start/end markers in the data itself — frame boundaries are detected purely by silence on the line (more on that in Advanced). The frame contents are compact binary:

Address1 byte
Function Code1 byte
DataN bytes
CRC-162 bytes

Address is the target slave's ID (0 is reserved for broadcast). CRC-16 protects the whole frame — transmitted low byte first, then high byte. A receiver that computes a different CRC than the one attached silently discards the frame.

Worked example Read 2 holding registers starting at address 0 from slave 17 (0x11):
11 03 00 00 00 02 C6 9B
= Address 0x11, FC 0x03 (Read Holding Registers), start address 0x0000, quantity 0x0002, CRC 0x9BC6 (sent as C6 9B). Try it yourself in the Frame Builder above — the defaults are already set to this exact example.
TCP

TCP Frame (MBAP Header)

Modbus TCP wraps the same function-code-plus-data payload in a 7-byte header called the MBAP header (Modbus Application Protocol), then hands the whole thing to TCP — no CRC needed, since Ethernet/TCP already checksum the data.

Transaction ID2 bytes
Protocol ID2 bytes
Length2 bytes
Unit ID1 byte
Function Code1 byte
DataN bytes
  • Transaction ID — set by the master, echoed back by the slave, so the master can match responses to requests on a connection that may have several in flight.
  • Protocol ID — always 0x0000 for Modbus.
  • Length — byte count of everything that follows (Unit ID + function code + data).
  • Unit ID — vestigial on pure TCP devices (often just 0x00 or 0xFF), but meaningful when a gateway is bridging to RTU slaves behind it (see Advanced).

Register Addressing — the 40001 Trap

This single convention causes more integration bugs than anything else in Modbus. On the wire, every address is a plain 0-based 16-bit number. But documentation has historically used a 5-digit convention where the leading digit encodes the table:

Documented asTableWire address
00001–09999Coils0–9998
10001–19999Discrete Inputs0–9998
30001–39999Input Registers0–9998
40001–49999Holding Registers0–9998
Where this bites you A device manual says "flow rate is in register 40013." Your master software asks for holding register address — is it 13, or 12? Depends whether your software's register field expects the documented number or the 0-based wire address. When in doubt, request address 12 first and check against a known value.

Exception Responses

When a slave can't honor a request, it replies with the function code OR'd with 0x80 (so 0x03 becomes 0x83), followed by a 1-byte exception code explaining why:

CodeMeaning
0x01Illegal Function — slave doesn't support this function code
0x02Illegal Data Address — the register/coil address doesn't exist on this slave
0x03Illegal Data Value — address is valid, but the value/quantity isn't
0x04Slave Device Failure — an internal error occurred processing the request

No response at all (a timeout) is different from an exception — it usually means a wiring issue, wrong slave ID, or wrong baud rate rather than a protocol-level complaint.

RTU

RS-485 Wiring Basics

Most Modbus RTU networks run over RS-485: a single twisted pair shared by every device on the bus (multi-drop), rather than a point-to-point link.

  • Termination — a 120Ω resistor at each physical end of the bus (not at every device) prevents signal reflections.
  • Biasing — pull-up/pull-down resistors keep the line in a known idle state when no device is transmitting, avoiding noise being read as data.
  • Daisy-chain, not star — devices should be wired in a line; star topologies cause reflections RS-485 wasn't designed to handle.
  • Distance/speed trade-off — roughly 1200 m at low baud rates (9600), much less at high baud rates.

RTU

CRC-16 Calculation

Modbus RTU uses CRC-16 with polynomial 0xA001 (the reversed form of 0x8005) and an initial value of 0xFFFF. You rarely need to hand-roll this — every Modbus library does it — but understanding it helps when you're debugging with a logic analyzer and need to verify a frame by hand.

uint16_t modbus_crc16(const uint8_t *data, int length) {
    uint16_t crc = 0xFFFF;
    for (int pos = 0; pos < length; pos++) {
        crc ^= data[pos];
        for (int i = 0; i < 8; i++) {
            if (crc & 0x0001) {
                crc >>= 1;
                crc ^= 0xA001;
            } else {
                crc >>= 1;
            }
        }
    }
    return crc;  // low byte transmitted first, then high byte
}

The CRC is computed over the address, function code, and data bytes — not including the CRC field itself, obviously.

RTU

RTU Frame Timing

RTU has no explicit frame delimiters, so devices rely on silence to know where one frame ends and the next begins:

  • A gap of at least 3.5 character times marks the start of a new frame.
  • A gap of 1.5 character times within a frame is treated as an error — the receiver discards what it has and waits for the next 3.5-character silence.

At low baud rates this works cleanly, but "character time" becomes impractically small at high speed. The Modbus spec addresses this directly: above 19200 baud, implementations should use a fixed 1.75 ms inter-frame gap and 0.75 ms inter-character gap rather than the literal character-time calculation.

Why this matters in practice A master polling too fast, or a slave with a slow UART buffer, can cause frames to be misread as continuations of the previous one. If you see sporadic CRC failures under load (but not when polling slowly), timing — not wiring — is usually the cause.

RTU-over-TCP vs Native Modbus TCP

These get confused constantly because both run over Ethernet on port 502, but they are not the same framing:

  • Native Modbus TCP uses the MBAP header described above — no CRC, no slave address byte (replaced by Unit ID).
  • Modbus RTU-over-TCP (sometimes called "Modbus RTU encapsulated in TCP") takes the literal RTU frame — address, function code, data, and CRC — and just tunnels those bytes over a TCP socket, with no MBAP header at all.

Some cheap serial-to-Ethernet converters do the latter instead of proper protocol translation. Symptom: a "Modbus TCP" device that a standards-compliant TCP master can't talk to, because it's actually expecting/sending raw RTU bytes with a CRC the master never generates. Always check which one a converter actually implements before assuming "TCP" means MBAP framing.

Gateways & the Unit ID

A Modbus TCP-to-RTU gateway lets a TCP master reach a bus of RTU slaves it has no direct serial connection to. This is exactly where the otherwise-vestigial Unit ID field earns its keep: the master puts the target RTU slave's address in the Unit ID byte, the gateway strips the MBAP header, builds a proper RTU frame (computing a fresh CRC) addressed to that slave ID, and sends it out the serial port — then does the reverse for the response.

Practical implication: when configuring software to talk to a device behind a gateway, the IP address gets you to the gateway, but the Unit ID still has to match the device's actual RTU slave address on the far side.

Endianness Pitfalls (32-bit Values)

A single Modbus register is only 16 bits. Representing a 32-bit value — a float, or a counter that exceeds 65535 — takes two consecutive registers, and here the spec says nothing about ordering. Different vendors do it differently:

LayoutRegister 1Register 2
Big-endian word orderHigh wordLow word
Little-endian word orderLow wordHigh word
Byte-swapped within each wordEither of the above, but with the two bytes inside each register also reversed
Debugging tip If a float reads as a wildly wrong number (or a sane-looking number that's off by a huge power of ten), you're almost certainly looking at the right two registers in the wrong order. Try swapping the register (word) order before swapping bytes — it's the more common culprit.

Security Considerations

Modbus — both RTU and TCP — has no built-in authentication, authorization, or encryption. It was designed for isolated, trusted industrial networks in an era before that was a problem. Anyone who can reach a Modbus TCP slave on port 502 can read or write any register it exposes, with no credentials required.

  • Never expose Modbus TCP (port 502) directly to the public internet — this is a well-documented, frequently-exploited ICS exposure.
  • Segment OT networks from IT/corporate networks; put Modbus traffic behind a firewall or VPN.
  • Modbus/TCP Security (an official extension, port 802) adds TLS — supported by some newer devices, but adoption is still limited.
  • Monitor for unexpected write commands (FC 0x05/0x06/0x0F/0x10) from unfamiliar hosts — a classic ICS attack pattern.

Tools & Debugging

  • Wireshark — has a native Modbus TCP dissector; decodes MBAP headers and function codes automatically. For RTU, you need a USB-to-serial tap and a protocol analyzer, or a logic analyzer plus manual decoding.
  • pymodbus (Python) — the most common open-source library for building a master or slave simulator in either RTU or TCP.
  • QModMaster / ModScan / Modbus Poll — GUI master simulators for manually poking registers on a real or simulated slave during bring-up.
  • diagslave / modpoll — lightweight command-line slave/master simulators, handy for CI or headless testing.

Code Example — Reading Registers in Python

Using pymodbus, the same read call works almost identically regardless of transport — only the client setup differs:

RTU 
from pymodbus.client import ModbusSerialClient

client = ModbusSerialClient(
    port="/dev/ttyUSB0",   # or "COM3" on Windows
    baudrate=9600,
    parity="N",
    stopbits=1,
    bytesize=8,
)
client.connect()

result = client.read_holding_registers(address=0, count=2, slave=17)
print(result.registers)

client.close()
TCP 
from pymodbus.client import ModbusTcpClient

client = ModbusTcpClient("192.168.1.50", port=502)
client.connect()

result = client.read_holding_registers(address=0, count=2, slave=1)
print(result.registers)

client.close()

Note slave= in both cases — for RTU it's the physical slave ID on the bus; for TCP it's the Unit ID (meaningful mainly when a gateway sits behind that IP).

Serial

Modbus ASCII Mode

Before RTU became the dominant serial mode, the original Modbus spec offered a second serial framing: ASCII mode. It's rare in new designs today, but still shows up on older equipment — and it's worth recognizing because its frames look completely different from RTU on the wire, even though the function codes and data model underneath are identical.

Instead of raw binary bytes, every byte is sent as two printable hex-digit ASCII characters. The frame is explicitly delimited rather than timing-based:

:start, 1 char
Address2 hex chars
Function2 hex chars
Data2N hex chars
LRC2 hex chars
CR LFend, 2 chars

Error checking uses an LRC (Longitudinal Redundancy Check) instead of CRC-16: sum every data byte (address through the last data byte), keep only the low 8 bits, then take the two's complement.

uint8_t modbus_lrc(const uint8_t *data, int length) {
    uint8_t lrc = 0;
    for (int i = 0; i < length; i++) {
        lrc += data[i];
    }
    return (uint8_t)(-((int8_t)lrc));  // two's complement
}
RTUASCII
EncodingRaw binaryPrintable hex ASCII
Framing3.5-char silenceExplicit : start, CRLF end
Error checkCRC-16LRC
Bytes on the wire1× the data~2× the data (plus delimiters)
Why you'd use itEfficiency (default choice today)Human-readable on a dumb terminal; more tolerant of modems/links with timing jitter, since it doesn't rely on precise inter-character silence

A master and slave must agree in advance which serial mode they're using (RTU or ASCII) — there's no auto-detection; configuring the wrong one just looks like silence or garbage on the line.

Ladder Logic Integration

On a PLC, Modbus communication is almost never "automatic" — a rung of ladder logic typically has to explicitly trigger each read or write, using a vendor-specific communication instruction or function block (common names: MSG, MB_CLIENT, MODBUS_MASTER, depending on platform). A minimal pattern looks like this:

Rung 1 — trigger a read every scan the enable bit is on
| MB_READ
slave=17 reg=0 qty=2 → Temp_Register |
Rung 2 — act on the value once the read completes
| Temp_Register > 1000 (Alarm) |

Rung 1's enable contact is usually a free-running clock bit or a "communication idle" flag rather than a one-shot, since Modbus reads need to repeat continuously to stay current — most platforms also expose a "done"/"error" bit pair from the instruction so the next rung can react to a failed read (timeout, exception response) rather than acting on stale or garbage data.

A second, increasingly common pattern skips explicit read/write rungs entirely: some PLCs and HMI/SCADA packages let you configure a cyclic Modbus I/O mapping once (device IP or serial port, slave ID, register ranges), and the platform polls automatically in the background, exposing each remote register as an ordinary local tag. Ladder logic then just reads Temp_Register like any other input — simpler to write, but you lose fine-grained control over poll timing and error handling for a specific transaction.

Design tip Don't issue a new Modbus request every single PLC scan (which can run at 10ms or faster) — most slaves can't keep up, and RTU buses especially will choke with collisions/timeouts. Gate requests with a timer (e.g. poll every 200–500ms) rather than the raw scan cycle.

Vendor Quirks

The spec is small, but real devices diverge from each other in the gaps it leaves open. A few patterns worth knowing before you integrate a specific device:

Schneider Electric / Modicon

As the protocol's creator, Schneider's own documentation (and much third-party documentation modeled on it) still leans on the classic 4xxxx-style register numbering described earlier. Their EcoStruxure/Unity software generally expects the documented number, not the raw 0-based address — check which one a given tool wants before assuming.

Siemens

S7-series PLCs don't speak Modbus natively out of the box — Siemens' own ecosystem is built around PROFIBUS/PROFINET instead. Talking Modbus from a Siemens PLC means adding a library block (MB_CLIENT/MB_SERVER in TIA Portal) and explicitly wiring up the communication port, rather than it being an inherent protocol option like it is on many competitors' PLCs.

VFDs (drives) — ABB, Danfoss, Yaskawa, etc.

Drives commonly expose a control word holding register that must be written with a specific bit pattern (enable, run, fault-reset bits) before the drive will accept a speed reference at all — a very common first-integration bug is writing only the speed register and wondering why the motor never turns. Speed/frequency values are also frequently scaled (e.g. a register value of 500 meaning 50.0 Hz) — always check the scaling factor in that drive's specific parameter manual, as it varies by vendor and sometimes by firmware version.

Energy meters — Schneider PM-series, Eastron SDM-series, etc.

Measurements (voltage, current, kWh) are usually IEEE-754 floats spread across two consecutive holding/input registers — and, as covered in Endianness Pitfalls, the word order is not standardized even within one manufacturer's own product lines. Always confirm against a known value (e.g. compare a live voltage reading to a multimeter) rather than assuming the same word order as the last meter you integrated.

WAGO / Beckhoff I/O

Modular I/O systems from these vendors often expose the same physical point through more than one Modbus table — e.g. a digital input available as both a Discrete Input and mirrored into a Holding Register bit for convenience — plus vendor-specific diagnostic registers (module status, fault codes) layered on top of the standard data model. Their register-map PDFs are essential reading; don't assume a "standard" layout.

The one rule that covers most of this section Never trust a generic assumption about scaling, word order, or addressing convention for a device you haven't integrated before — open that specific model's register map document first. The protocol is standardized; what a given vendor puts behind it is not.
Serial

Diagnostic Function Code (0x08)

Function code 0x08 is specific to serial lines (RTU/ASCII) and is used to test and diagnose the communication link itself, separately from reading or writing application data. The data field starts with a 2-byte sub-function code that picks what kind of diagnostic to run:

Sub-functionNameWhat it does
0x00Return Query DataLoopback test — the slave echoes back exactly the data it was sent
0x01Restart Communications OptionResets the slave's serial communication state/counters
0x0AClear Counters and Diagnostic RegisterZeroes all the diagnostic counters below
0x0BReturn Bus Message CountTotal messages the slave has detected on the bus
0x0CReturn Bus Communication Error CountCRC/framing errors detected
0x0DReturn Bus Exception Error CountNumber of exception responses this slave has sent
0x0EReturn Slave Message CountMessages addressed specifically to this slave

In practice, Return Query Data (0x00) is the one you'll reach for most: it's the standard "is this device alive and framing correctly" test, without touching any application register — useful when you suspect a wiring or baud-rate issue but don't want side effects from poking real registers.

Worked example Request: 11 08 00 00 A5 37 (slave 0x11, sub-function 0x0000, data 0xA537). A healthy slave replies with the identical frame — same function code, same data — confirming the link is up and correctly framing requests.

Modbus vs. Other Industrial Protocols

Modbus is rarely the only option on the table. Knowing where it sits relative to the alternatives helps answer "should this actually be Modbus?" before you commit to it.

ModbusPROFINETEtherNet/IPBACnetOPC UA
Typical domainGeneral industrial, legacy-friendlyFactory automation (Siemens ecosystem)Factory automation (Rockwell ecosystem)Building automation (HVAC, lighting, fire)IT/OT convergence, IIoT
TransportSerial or plain TCPEthernet, real-time classesStandard Ethernet + CIPIP, MS/TP serial, EthernetTCP or HTTPS, pub/sub variants
Built-in securityNoneHistorically weak, improvingCIP Security extensionBACnet/SC adds TLSYes — certificates, encryption, auth from the start
Real-time determinismNoYes (RT/IRT, sub-ms)ModerateNot a priority (slow timescales)Not inherent (TSN extensions exist)
Implementation complexityVery lowHighMedium-highMediumHigh (rich information modeling)
Best fitQuick integrations, legacy device supportHigh-speed motion controlRockwell-centric plantsHVAC/BMS specificallyModern architectures needing built-in security and semantic data

Rule of thumb: reach for Modbus when you need something simple, well-understood, and supported by nearly every device on the market — especially retrofitting older equipment. Reach for PROFINET or EtherNet/IP when you need hard real-time motion control within one vendor's ecosystem. Reach for BACnet specifically for building/HVAC systems. Reach for OPC UA when security and a rich, vendor-neutral information model matter more than minimal implementation effort — increasingly the default choice for new IIoT architectures that need to talk to the IT side of the business securely.

Frame: 11 03 00 6B 00 03 76 87

Identify every field: slave address, function code, and what it's requesting.

Basic Convert a documented register number

A meter's manual says "line voltage is in register 30007." What table does this belong to, and what's the 0-based wire address you'd actually request?

Answer The 3xxxx prefix means Input Registers. Wire address = 30007 − 30001 = 6. You'd issue a Read Input Registers (FC 0x04) request starting at address 6.
Intermediate Construct a write request

Write the RTU request bytes (everything except the CRC) to write the value 1500 to a single holding register at wire address 10, on slave 5.

Answer 05 06 00 0A 05 DC
05 = slave 5 · 06 = Write Single Register · 00 0A = address 10 · 05 DC = 1500 in hex (0x05DC).
Intermediate Decode a TCP/MBAP frame

Frame (as sent over the TCP socket): 00 01 00 00 00 06 01 03 00 00 00 02

Decode the full MBAP header plus the PDU.

Answer Transaction ID = 0x0001 · Protocol ID = 0x0000 · Length = 0x0006 (6 bytes follow) · Unit ID = 0x01 · Function code = 0x03 (Read Holding Registers) · Start address = 0x0000 · Quantity = 0x0002. Notice: no CRC anywhere — TCP/Ethernet already guarantees data integrity.
Advanced Decode an exception response

A master sends a Read Holding Registers request to slave 17 and gets back: 11 83 02 C1 34. What happened?

Answer 83 = 0x03 | 0x80 → this is an exception response to function code 0x03. The exception code 02 means Illegal Data Address — the register range requested doesn't exist on this slave. Check the start address and quantity against that slave's actual register map.
Advanced Spot the bug

Your code reads a 32-bit temperature float from two holding registers and has worked correctly for months against Meter A. You add Meter B from a different manufacturer, same register layout on paper, same code path — and now the temperature reads as either a huge meaningless number or NaN. What's almost certainly wrong, and what would you check first?

Answer Word/byte order for 32-bit values isn't standardized by the Modbus spec — Meter B very likely stores its float with a different register (and/or byte) order than Meter A. Check Meter B's register map document for its specific word-order convention, and try swapping the two registers' order before assuming anything else is broken.
Advanced Diagnose with function code 0x08

A slave on an RS-485 bus intermittently stops responding to application reads (FC 0x03/0x04). Before assuming the device itself is faulty, what's a low-risk first check you could run against it, and how would you interpret the result?

Answer Send a Diagnostics (FC 0x08) Return Query Data request (sub-function 0x00) with some arbitrary data. If the slave echoes it back correctly, the serial link itself (wiring, termination, baud rate, addressing) is fine and the issue is more likely application-level (e.g. it's busy, or rejecting that specific register range) — if it doesn't respond even to the loopback test, suspect the physical link (wiring, termination resistors, baud rate mismatch) before the device's application logic.
