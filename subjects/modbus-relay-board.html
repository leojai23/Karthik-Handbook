Modbus RTU 4-Channel Relay Board

How the wiring actually works, how to bring the board up from a cold start, and a complete home-automation build using it as the Modbus slave. Companion to the Modbus RTU/TCP tutorial — this page is the hands-on hardware half.

01 What's on the board

Three separate circuits share this board, and keeping them mentally separate is most of what makes wiring go smoothly: a power circuit (12V in), a control circuit (RS485, low-voltage logic), and a switched-load circuit per relay (whatever you're turning on and off — potentially mains voltage, electrically isolated from the other two by the relay's dry contacts).

TerminalWhat it is
DC12VPower in, 12V DC barrel jack or screw terminal
A+ / B-RS485 differential pair — the entire control interface
IN1–IN4Opto-isolated digital inputs, read via function code 02
K1–K4Relay dry contacts (NO/COM/NC), switched via function code 05

02 Why the default address matters

Out of the box the board answers to address 01 at 9600 8N1 — no setup needed for one board. Addressing only becomes a decision once a second board joins the same bus, because RS485 is multi-drop: every device shares the same two wires, and the address in each command is how the right one knows to answer.

To move a fresh board from 01 to 02 before joining it to a bus that already has a 01, send this to it alone first (broadcast address 00, function 06, write to register 4000):

000640 0000 021c 1a

Verified against CRC-16/Modbus (poly 0xA001, init 0xFFFF) before being used anywhere on this page — see the Frame Builder & Checksum Calculator in the main tutorial if you want to check your own frames the same way.

03 Bringing one board up

  1. Power it

    12V DC into the barrel jack or the DC12V/GND terminals. The power LED and the D5 running LED should both light immediately — if neither does, check polarity before anything else.

  2. Wire RS485

    Board A+/B- to your USB–RS485 adapter's A/B. Tie GND between board and adapter if they aren't sharing a supply, to keep the differential signal riding on a common reference. If you get silence on every command, swap A and B before suspecting anything else — it's the single most common RS485 wiring mistake.

  3. Set the serial parameters

    9600 baud, 8 data bits, no parity, 1 stop bit — the board's fixed default. No configuration step required for this.

  4. Confirm it answers

    Send a read on all four relay states and look for a reply:

    010100 0100 046c 09

    No reply after ~500ms almost always means wiring (A/B swapped, missing GND) rather than the board itself — the module doesn't need any setup to respond to this.

  5. Switch something

    Relay 1 on, then off — note this board uses 01 00 for "on", not the Modbus-standard FF 00, which matters if you later swap in a generic Modbus library:

    010500 0101 009d 9a
    010500 0100 009c 0a
Before wiring a real load If a relay channel is going to switch anything above extra-low voltage (mains lighting, a pump motor), that load-side wiring should be done with the same care as any mains work — isolated, fused appropriately for the load, and ideally by someone comfortable with it. Everything on the control side of the relay (RS485, 12V logic supply) stays low-voltage and safe to prototype freely; it's only the K1–K4 contacts that can carry something dangerous.

04 Home automation example

Four relays map naturally to four loads, with one physical wall switch wired into IN1 as an override the software can see. The Pi is the Modbus master: it polls the board on a short interval and acts on what it reads.

Wall-switch override (poll loop)

The board never links inputs to relays on its own — the datasheet is explicit that IN1–IN4 are read-only status bits. The mapping from "switch pressed" to "relay on" is entirely your script's job:

import serial, time

PORT = "/dev/ttyUSB0"   # Windows: "COM5"
ser = serial.Serial(PORT, 9600, bytesize=8, parity="N", stopbits=1, timeout=0.5)

RELAY1_ON  = bytes.fromhex("01 05 00 01 01 00 9d 9a")
RELAY1_OFF = bytes.fromhex("01 05 00 01 00 00 9c 0a")
READ_INPUTS = bytes.fromhex("01 02 00 00 00 00 78 0a")

def read_in1():
    ser.write(READ_INPUTS)
    time.sleep(0.05)
    resp = ser.read(6)                 # 01 02 01 <status> <crc_lo> <crc_hi>
    return len(resp) >= 4 and bool(resp[3] & 0x01)

last = False
while True:
    pressed = read_in1()
    if pressed and not last:
        ser.write(RELAY1_ON)
    elif not pressed and last:
        ser.write(RELAY1_OFF)
    last = pressed
    time.sleep(0.2)

Porch light + pump on a schedule

No input wiring needed for this half — just time-triggered writes to K3 and K4:

import schedule, time

RELAY3_ON  = bytes.fromhex("01 05 00 03 01 00 3c 5a")
RELAY3_OFF = bytes.fromhex("01 05 00 03 00 00 3d ca")

schedule.every().day.at("18:30").do(lambda: ser.write(RELAY3_ON))
schedule.every().day.at("23:00").do(lambda: ser.write(RELAY3_OFF))

while True:
    schedule.run_pending()
    time.sleep(1)
Why raw frames instead of a Modbus library pymodbus's write_coil(True) sends the standard FF 00, which this board doesn't treat as "on" — it wants 01 00. Raw byte frames sidestep that mismatch entirely and match exactly what's verified on this page.
