Why Python for Automation

Core

Python shows up throughout this Handbook's worked examples — the Modbus tutorial's RTU master, the Raspberry Pi tutorial's GPIO and Modbus-polling code, the ESP32 tutorial's gateway concept — for the same reasons it dominates automation scripting generally: readable enough that a quick field script stays maintainable, an enormous standard library (serial ports, sockets, binary parsing, all built in or one pip install away), and a vast ecosystem of protocol-specific libraries (pymodbus, paho-mqtt, opcua) that mean the hard protocol work rarely needs reinventing from scratch.

Talking to Serial Ports: pyserial

Field

The pyserial library (import serial) is the standard way to open an RS-485/RS-232 connection — exactly the pattern already used in the Modbus and Raspberry Pi tutorials:

import serial

ser = serial.Serial(
    port="/dev/ttyUSB0",   # or "COM5" on Windows
    baudrate=9600,
    bytesize=8, parity="N", stopbits=1,
    timeout=0.5             # read() returns after this many seconds even with no data
)
ser.write(bytes.fromhex("01 03 00 00 00 02"))
response = ser.read(9)      # read up to 9 bytes, or until timeout
ser.close()

The timeout parameter matters enormously: without it, read() blocks forever waiting for bytes that may never arrive from a disconnected or unresponsive device — exactly the scenario the Timeouts & Retries section below is built to handle gracefully instead of hanging the whole program.

Talking to Sockets: TCP Clients

Field

For Modbus TCP, OPC UA, or any other Ethernet-based protocol, Python's built-in socket module is the equivalent of pyserial for the network:

import socket

sock = socket.create_connection(("192.168.1.50", 502), timeout=2.0)
sock.sendall(bytes.fromhex("00 01 00 00 00 06 01 03 00 00 00 02"))
response = sock.recv(256)
sock.close()

Most real projects reach for a dedicated library (pymodbus for Modbus, for instance) rather than hand-rolling frames like this — but understanding what's happening underneath, at the raw socket level, is exactly what makes debugging a misbehaving library call tractable instead of mysterious.

Packing & Unpacking Binary Data

Core

Field protocols speak raw bytes; Python code wants numbers. The struct module bridges the two, with a format string encoding both byte order and data type — the exact same ABCD/DCBA byte-order concepts from the Electronics & Instrumentation tutorial's endianness section, expressed directly as code:

import struct

# Two Modbus holding registers (big-endian byte order, "ABCD" register order)
# containing the IEEE-754 bit pattern for pi: 0x4049, 0x0FDB
raw = struct.pack('>HH', 0x4049, 0x0FDB)
value = struct.unpack('>f', raw)[0]
print(value)   # 3.1415927410125732

The leading character sets byte order (> big-endian, < little-endian), and the following letters set the type (H unsigned 16-bit, f 32-bit float, and so on). Get the byte order wrong and the number decodes to nonsense without any error at all — exactly the class of bug the Modbus tutorial's endianness section warns about, and exactly why this deserves deliberate attention rather than guessing. Try different combinations in the Struct Format Code Builder above.

Virtual Environments & Dependencies

Core
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install pyserial pymodbus paho-mqtt
pip freeze > requirements.txt

A virtual environment keeps one project's library versions isolated from every other project (and from the system Python) — essential once more than one automation script lives on the same machine, since two projects wanting different versions of the same library is a question of when, not if. requirements.txt records exactly what's needed, so a deployment to a new Raspberry Pi or gateway device is pip install -r requirements.txt, not a guessing game.

Logging Instead of print()

Core
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s",
    filename="poller.log"
)

logging.info("Connected to device at 192.168.1.50")
logging.warning("Device 3 timed out, retrying")
logging.error("Device 7 unreachable after 5 attempts")

print() output vanishes the moment a terminal closes, carries no timestamp, and has no concept of severity. For anything meant to run unattended — the systemd services covered in the Raspberry Pi tutorial, or any long-running poller — logging gives timestamped, severity-leveled, file-persisted output essentially for free, which is exactly what's needed to answer "what happened at 3am when nobody was watching" after the fact.

Structuring a Polling Loop

Field

Every Modbus master, MQTT publisher, and sensor logger in this Handbook ultimately boils down to the same shape:

import time

def poll_all(devices):
    for device in devices:
        try:
            value = read_device(device)
            handle_value(device, value)
        except DeviceError as e:
            logging.warning(f"{device.name} failed: {e}")
            continue   # move on — one bad device shouldn't stop the rest

while True:
    start = time.monotonic()
    poll_all(devices)
    elapsed = time.monotonic() - start
    time.sleep(max(0, CYCLE_TIME - elapsed))

time.monotonic(), not time.time(), is the right clock for measuring elapsed time — it can't jump backward if the system clock gets adjusted (NTP sync, manual change), where time.time() can.

Error Handling for Flaky Devices

Field

Field devices fail in mundane, expected ways: a timeout, a dropped connection, a malformed response from electrical noise on the line. The discipline that matters is catching specific exceptions, not reaching for a bare except::

try:
    response = ser.read(expected_length)
    if len(response) != expected_length:
        raise TimeoutError("short read — device didn't respond in time")
    value = decode(response)
except (serial.SerialException, TimeoutError) as e:
    logging.warning(f"Device {addr}: {e}")
    continue
# a genuine bug (e.g. a TypeError from bad code) is NOT caught here,
# and will surface loudly instead of being silently swallowed

A bare except: catches everything — including a real bug in your own code, a KeyboardInterrupt from someone trying to stop the script, even a memory error — and silently continuing past any of those hides problems rather than solving them. Catch the specific, expected failure modes of the I/O you're doing; let anything else propagate and be seen.

Timeouts & Retries with Backoff

Field

A single retry immediately after a failure often just repeats the same failure (the device is still busy, the noise burst hasn't passed). Exponential backoff spaces retries out, giving a struggling device time to recover:

def read_with_retry(device, max_attempts=5, base=0.5, cap=8.0):
    for attempt in range(max_attempts):
        try:
            return read_device(device)
        except DeviceError as e:
            if attempt == max_attempts - 1:
                raise
            delay = min(cap, base * (2 ** attempt))
            logging.warning(f"{device.name} attempt {attempt+1} failed, retrying in {delay}s")
            time.sleep(delay)

Worked example: attempt index 3 with base=0.5s, cap=8s gives min(8, 0.5 × 2³) = 4.0s. Across 5 full attempts at 2s timeout each, the worst-case total time before giving up is 5×2 + (0.5+1+2+4) = 17.5s — confirm both in the calculators above, and size your overall polling cycle time with that worst case in mind, not just the happy-path timing.

Keeping the device list — addresses, register maps, units — in a JSON (or YAML) file rather than hardcoded in the script means adding or re-addressing a field device is a config edit, not a code change and redeploy. This is exactly the kind of data the Modbus tutorial's register-map tables and the Control Panel Design tutorial's as-built documentation both describe conceptually; a config file is where that documentation becomes something the running code actually reads.

Logging to CSV & SQLite

Core

Expanding on the data-logging pattern from the Raspberry Pi tutorial: a plain CSV file (via the built-in csv module) is the simplest option, perfectly fine for a single stream of readings opened later in a spreadsheet. SQLite (via the built-in sqlite3 module — no separate database server needed) scales better once there's more than one device, concurrent writes, or a need to query by time range rather than just appending:

import sqlite3
conn = sqlite3.connect("readings.db")
conn.execute("""CREATE TABLE IF NOT EXISTS readings
    (ts REAL, device TEXT, value REAL)""")
conn.execute("INSERT INTO readings VALUES (?, ?, ?)",
             (time.time(), "Tank 3 Level", 289.35))
conn.commit()

Concurrency: Threading for Parallel Polling

Core

The sequential polling loop above has a real cost: if device 3 of 20 takes its full timeout to fail, every device after it waits. Python's Global Interpreter Lock (GIL) prevents true CPU-level parallelism, but it's released during I/O waits — exactly what reading a serial port or socket mostly is — so threading still meaningfully helps throughput for I/O-bound polling like this:

from concurrent.futures import ThreadPoolExecutor

def poll_all_threaded(devices, max_workers=10):
    with ThreadPoolExecutor(max_workers=max_workers) as pool:
        results = pool.map(read_with_retry, devices)
    return list(results)

Asyncio as an Alternative

Core

asyncio achieves a similar goal — many I/O operations in flight at once — through cooperative coroutines instead of OS threads, which scales to far more concurrent connections with lower overhead, at the cost of needing every library in the call chain to be async-aware (a blocking pyserial call inside an async function stalls the entire event loop, defeating the purpose). Threading is usually the simpler starting point for a modest number of devices (tens); asyncio pays off more clearly at larger scale (hundreds of connections) where thread overhead itself becomes the bottleneck — async-native libraries exist for both Modbus and MQTT if that scale is genuinely needed.

A Long-Running Service

Field

Pairs directly with the Raspberry Pi tutorial's systemd section: the Python side needs to shut down cleanly when systemd sends a stop signal, rather than being killed mid-write:

import signal

running = True
def handle_stop(signum, frame):
    global running
    running = False

signal.signal(signal.SIGTERM, handle_stop)

while running:
    poll_all(devices)
    time.sleep(1)

logging.info("Shutting down cleanly")
cleanup()  # close ports, flush logs, etc.

Testing Without the Hardware

Core

A polling script is hard to test if every test run needs the real field device plugged in. Two common approaches: mock the serial/socket object entirely (Python's built-in unittest.mock can stand in for serial.Serial, returning canned byte responses to verify the decoding logic in isolation), or run against a software simulator (a Modbus slave simulator listening on a local port, standing in for the real device) for more realistic end-to-end testing. Either approach lets the decoding and error-handling logic — the parts most likely to have subtle bugs — be verified automatically and repeatedly, the same discipline behind every verified worked example throughout this Handbook, just automated.

Packaging a Reusable Module

Core

Once the same Modbus-read-with-retry or MQTT-publish helper gets copy-pasted into a third project, it's time to extract it into its own small importable module (a single .py file, or a proper package with a pyproject.toml once it's substantial) rather than maintaining three divergent copies. This is the same DRY principle behind any software project, applied to the field-communication helpers this tutorial has built up — a field_io.py with the retry/backoff/logging logic once, imported everywhere it's needed.

A Resilient Multi-Protocol Poller

Field

Pulling every piece of this tutorial together into the shape a real deployment takes: a threaded pool polls several Modbus RTU devices on a schedule, each read wrapped in retry-with-backoff and narrow exception handling; successful readings are logged to SQLite and published to an MQTT broker (the ESP32 & IoT tutorial's pattern, here running on a Pi or small PC instead of a microcontroller); device addresses and register maps live in a JSON config file, not hardcoded; the whole thing runs as a systemd service with clean signal-handling shutdown; and the decode logic has unit tests that run with no hardware attached at all. No single piece here is exotic — the skill is in applying all of them together, consistently, the same conclusion the Control Panel Design tutorial's worked example reached from the hardware side.

Basic Compute a backoff delay

Using delay = min(cap, base × 2attempt) with base=0.5s and cap=8s, what's the delay for attempt index 3?

Answer min(8, 0.5 × 2³) = min(8, 4.0) = 4.0s.
Intermediate Compute a worst-case retry timeout

A read is attempted up to 5 times, 2s timeout each, with exponential backoff (base=0.5s, cap=8s) between attempts. What's the worst-case total time before giving up?

Answer 5 timeouts: 5 × 2 = 10s. Plus 4 backoff delays between attempts: 0.5+1+2+4 = 7.5s. Total: 17.5s.
Intermediate Check whether a polling cycle fits its budget

20 devices, each taking 50ms to poll, need to fit inside a 1-second cycle. Does it fit, and what's the achieved rate?

Answer 20 × 0.05 = 1.0s — exactly fits, with zero slack. Achieved rate: 1/1.0 = 1.0Hz. In practice this is a risky fit with no margin for a single retry; either fewer devices, faster per-device timeouts, or threading (see Advanced) would give real headroom.
Advanced Diagnose an overloaded polling cycle

The same 1-second cycle now needs to cover 50 devices at 50ms each. Does it fit, and what are two ways to fix it?

Answer 50 × 0.05 = 2.5s — well over the 1s budget; the actual cycle would run at 0.4Hz, less than half the desired rate. Fixes: poll devices concurrently with a thread pool (Advanced section above) so the 2.5s of work overlaps instead of stacking sequentially, or relax the desired cycle time to something the sequential approach can actually sustain.
Advanced Explain why bare except: is dangerous in a polling loop

A polling loop wraps each device read in try: ... except: continue (a bare except with no exception type). What's the risk, and what should it catch instead?

Answer A bare except: catches everything, including real bugs in the decoding code (a TypeError or IndexError from malformed data), KeyboardInterrupt from an operator trying to stop the script, and system-level exceptions — all silently swallowed and the loop just continues, hiding problems that should have been visible. It should instead catch only the specific, expected I/O failure types (e.g. serial.SerialException, a custom TimeoutError), letting anything else propagate and be seen.
