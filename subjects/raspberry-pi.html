What Is a Raspberry Pi

Hardware

A Raspberry Pi is a full single-board computer — it boots a real operating system (usually Linux-based Raspberry Pi OS), runs a general-purpose CPU, and has networking, USB, and a 40-pin GPIO header for hardware interfacing, all on a board roughly the size of a credit card. It sits in a different category from both the microcontrollers covered implicitly in the Electronics tutorial and the PLCs covered in the PLC Learning tutorial: more computing power and flexibility than either, but — critically — without a PLC's deterministic scan cycle or certified I/O, a distinction covered in full in Pi vs PLC below.

Good fits: data logging, dashboards, Modbus/network gateways, image processing, anything needing a real OS and real compute. Poor fits: anything safety-critical, or anything needing guaranteed microsecond-level timing — that's a microcontroller's or a PLC's job.

Powering & Booting

Hardware

Modern Pi boards (4 and later) take power over USB-C and boot from a microSD card or USB storage; older boards use micro-USB power and SD only. Undersized power supplies are a frequent, under-diagnosed cause of random crashes and corrupted SD cards — use the official or an equivalently-rated supply for your specific board rather than whatever USB charger is closest to hand.

Raspberry Pi Imager (the official flashing tool) writes Raspberry Pi OS to the SD card or USB drive and can pre-configure hostname, SSH, WiFi, and a user account before first boot — the standard starting point for a headless install (see below), skipping the need to ever attach a monitor and keyboard at all.

First Boot & Headless Setup

Software

A "headless" Pi runs with no monitor or keyboard attached, administered entirely over the network via SSH. With Imager's pre-configuration (enabling SSH and entering WiFi credentials before the first boot), the Pi comes up already reachable:

ssh username@raspberrypi.local

From there, sudo raspi-config is the standard menu-driven tool for everything else first-boot related: expanding the filesystem to use the full SD card, enabling I2C/SPI (both off by default — see those sections below), setting the locale/timezone, and changing the default password.

GPIO Fundamentals: Pins, Voltage & Current

Hardware

The single most important electrical fact about the Pi: its GPIO pins run at 3.3V logic and are not 5V tolerant. Applying 5V directly to a GPIO pin risks permanently damaging it — there's no built-in protection the way some other boards provide. Every 5V sensor or module needs a level shifter or voltage divider (see the Level-Shift tool above) before it ever touches a GPIO pin.

Current is limited too: a commonly cited guideline is roughly 16mA maximum from any single pin, with the total across all GPIO pins combined kept under about 50mA — these numbers vary slightly by board revision, so treat them as a safe working rule rather than an exact spec. This is nowhere near enough to drive a relay coil, a motor, or anything beyond a small LED directly; anything bigger needs a transistor, MOSFET, or relay module driven by the GPIO pin rather than powered directly from it — precisely the transistor-as-switch pattern from the Electronics tutorial.

Pins are numbered two ways, and mixing them up is a common source of "wrong pin" bugs: BCM numbering refers to the Broadcom SoC's internal GPIO numbers (what most code uses, e.g. "GPIO17"); BOARD numbering is simply the physical pin position counting across the 40-pin header (1–40). Always check which scheme a library or tutorial is using before wiring.

The one rule that prevents the most damage Never connect a GPIO pin directly to anything that might be at 5V, and never try to drive anything beyond a small LED straight from a GPIO pin. Both mistakes are common, both are usually fatal to the board or the pin.

Digital Output: Driving an LED

Hardware

The canonical first circuit: GPIO pin → current-limiting resistor → LED → ground. Using the LED Resistor Calculator above with a typical red LED (Vf ≈ 1.8V) at a conservative 8mA from the Pi's 3.3V rail gives a resistor of about 187.5Ω — round up to the nearest standard value (220Ω is the usual safe, readily-available choice).

Digital Input: Reading a Button

Hardware

A button wired between a GPIO pin and ground needs a defined state when not pressed, or the input floats and reads randomly. Two options: an external pull-up/pull-down resistor, or — far more common on the Pi — the SoC's own internal pull-up/pull-down resistors, enabled in software with no extra wiring at all. With an internal pull-up enabled, the pin reads HIGH when the button is open and LOW when it's pressed (pulled to ground) — inverted logic that trips up a lot of beginners expecting "pressed = HIGH."

Python on the Pi: GPIO Libraries

Software

Python is the default language for Pi GPIO work, with two common libraries: the lower-level RPi.GPIO, and the friendlier gpiozero, which wraps common components (LEDs, buttons, motors, sensors) as ready-made classes:

from gpiozero import LED
from time import sleep

led = LED(17)   # BCM numbering
while True:
    led.on()
    sleep(1)
    led.off()
    sleep(1)

PWM on the Pi

Software

Pulse Width Modulation switches a pin on and off rapidly, and the fraction of time it's on (duty cycle) determines the effective average output — used for LED dimming, DC motor speed (in combination with a driver, since GPIO current is far too low to drive a motor directly), and servo position (see below). Most GPIO pins support software PWM (timed in software, usable on any pin, with a little jitter); a small number of pins support hardware PWM (timed by dedicated silicon, far more precise) — check your specific board's pinout for which pins those are before relying on hardware PWM for anything timing-sensitive like a servo.

Controlling a Servo

Hardware

A standard RC servo takes one PWM signal wire, plus power and ground, and expects a pulse every 20ms (50Hz) whose width — not duty cycle — sets its angle: roughly 1ms for one end of travel, 2ms for the other, 1.5ms for centre.

Worked example: commanding 135° with the common 1ms=0°/2ms=180° convention: pulse = 1 + (135/180) = 1.75ms. Verify it in the calculator above.

Power the servo separately A servo under any real load draws far more current than a GPIO pin can supply (or than the Pi's own 5V rail can comfortably provide for more than one servo). Power the servo from its own 5–6V supply, with only the signal wire and a shared ground going to the Pi — never try to run the servo's power from a GPIO pin.

I2C Communication

Hardware

I2C is a two-wire bus — SDA (data) and SCL (clock) — letting multiple devices share the same two pins, each identified by its own address. On the Pi's 40-pin header, the primary I2C bus is fixed to GPIO2 (SDA, physical pin 3) and GPIO3 (SCL, physical pin 5). It's disabled by default; enable it via raspi-config or by uncommenting it in /boot/config.txt, then confirm what's connected with:

i2cdetect -y 1

which scans the bus and prints a grid of addresses, showing exactly which devices respond — invaluable for confirming wiring before writing a single line of driver code.

SPI Communication

Hardware

SPI is faster than I2C but uses more pins: MOSI (data out), MISO (data in), SCLK (clock), and one Chip Select line per device. The Pi's primary SPI bus uses GPIO10 (MOSI, pin 19), GPIO9 (MISO, pin 21), GPIO11 (SCLK, pin 23), and GPIO8/GPIO7 (CE0/CE1, pins 24/26) for up to two devices on the one bus without extra wiring. Like I2C, it's off by default and enabled through raspi-config.

The Pi Has No Analog Input

Hardware

Unlike most microcontrollers, no Raspberry Pi model has a built-in ADC — every GPIO pin is strictly digital, reading only HIGH or LOW. Any analog sensor (a potentiometer, a simple analog temperature sensor, anything not already speaking a digital protocol) needs an external ADC chip in between, almost always talking I2C or SPI.

Serial/UART & RS-485

Hardware

The Pi's GPIO header includes a UART (GPIO14/15, TX/RX) for direct serial connections, but the far more common approach for field devices is a USB-to-RS485 adapter — simpler, electrically isolated from the Pi's own 3.3V domain, and exactly the setup used throughout the Modbus tutorial's Python examples. This is the Pi's on-ramp into industrial field buses: once it can open a serial port, it can speak Modbus RTU to anything on an RS-485 line.

Interfacing Relays Safely

Hardware

Switching mains-voltage or motor-level loads from a Pi always goes through a relay or solid-state relay module — never direct GPIO control of the load itself. A GPIO pin switches the relay's low-voltage control side; the relay's separate, physically isolated contacts do the actual high-voltage switching. Opto-isolated relay modules (the same isolation principle from the Electronics tutorial's Signal Conditioning section) add a further layer of protection, keeping a fault on the high-voltage side from ever reaching the Pi's GPIO pins at all.

Raspberry Pi as a Modbus Master

Software

With a USB-RS485 adapter, a Pi running Python can act as a full Modbus RTU master, polling exactly the kind of relay boards and 4–20mA transmitters covered in this Handbook's other subjects:

import serial, time

ser = serial.Serial("/dev/ttyUSB0", 9600, bytesize=8, parity="N", stopbits=1, timeout=0.5)

READ_COILS = bytes.fromhex("01 01 00 01 00 04 6c 09")  # verified frame, see Modbus tutorial
ser.write(READ_COILS)
time.sleep(0.05)
response = ser.read(8)
print(response.hex())

This is the same byte-level approach as the Modbus tutorial's worked examples — the Pi is simply the computer running the Python master instead of a desktop PC, with the advantage of being small and cheap enough to sit permanently next to the field equipment it's polling.

Running Code Reliably: systemd

Software

A script launched manually from a terminal stops the moment that terminal closes or the Pi reboots. For anything meant to run continuously — a Modbus polling loop, a dashboard server — wrap it as a systemd service, which starts automatically at boot and restarts automatically if the script crashes:

[Unit]
Description=Modbus polling service
After=network.target

[Service]
ExecStart=/usr/bin/python3 /home/pi/poll.py
Restart=always
User=pi

[Install]
WantedBy=multi-user.target

Saved as /etc/systemd/system/modbus-poll.service and enabled with sudo systemctl enable --now modbus-poll, this is the standard way to turn a script into something that behaves like a real, unattended embedded application rather than something that quietly stops the first time the Pi reboots after a power blip.

Pi vs PLC: Real-Time Limitations

Software

A standard Raspberry Pi runs a general-purpose Linux kernel, not a real-time operating system. That means the OS scheduler can, at any moment, briefly delay a running script to service something else — usually imperceptible, but enough jitter (typically single-digit milliseconds, occasionally more under load) that a Pi cannot guarantee the same scan-to-scan timing determinism a PLC's dedicated firmware does, as covered in the PLC Learning tutorial's scan cycle section. For data logging, dashboards, and Modbus polling, this jitter is irrelevant. For anything safety-related, or anything needing hard real-time guarantees (a fast closed PID loop, precise multi-axis motion coordination), it's a genuine limitation — and exactly the territory the PLC Learning tutorial's Safety Interlocking section already warned belongs on certified, purpose-built hardware, not general-purpose compute.

Where this actually matters A Pi reading a sensor once a second for a dashboard: jitter is irrelevant. A Pi trying to be the safety interlock for a machine, or to hit a hard timing deadline every single cycle without exception: use a PLC or a real-time-capable microcontroller instead.

Remote Access & Security Basics

Software

A handful of habits separate a reasonably secure headless Pi from an easy target: change the default password immediately (a default-credential Pi exposed to the internet is found and compromised by automated scanners, typically within hours); prefer SSH key authentication over password login, disabling password auth entirely once a key is set up; keep the OS updated (sudo apt update && sudo apt full-upgrade); and never expose SSH directly to the open internet — use a VPN or SSH tunnel if remote access from outside the local network is genuinely needed.

Data Logging & a Simple Dashboard

Software

A natural next step once sensor data is flowing (whether from a direct GPIO/I2C/SPI sensor or a polled Modbus device) is persisting it — a lightweight SQLite database or even a plain CSV file for simple cases — and serving a small live view with a minimal web framework like Flask, reachable from any browser on the local network. This is the same sensor-to-dashboard pattern used throughout this Handbook's worked home-automation examples, just generalized: sense, log, display.

GPIO Expansion: HATs

Hardware

A HAT (Hardware Attached on Top) is a standardized add-on board that stacks directly onto the 40-pin header, identifying itself to the OS automatically via an onboard EEPROM so drivers and overlays load without manual configuration. This covers most common expansion needs — additional relays, ADCs, motor drivers, displays — without hand-wiring a breadboard, at the cost of less flexibility than wiring the equivalent chips individually.

Basic Size an LED resistor for the Pi's 3.3V rail

A red LED (Vf = 1.8V) needs to be driven at a conservative 8mA from a Pi GPIO pin's 3.3V output. What resistor value is needed?

Answer R = (3.3 − 1.8) / 0.008 = 1.5/0.008 = 187.5Ω. Round up to the nearest standard value, typically 220Ω, confirmed in the calculator above.
Basic Check a GPIO current budget

Five LEDs are driven directly from five different GPIO pins, each at 8mA. Using the commonly cited ~50mA total GPIO current guideline, is this within budget?

Answer 5 × 8mA = 40mA total — under the ~50mA guideline, so this is fine, though it doesn't leave much headroom for anything else drawing from GPIO at the same time.
Intermediate Find a servo pulse width for a given angle

Using the common 1ms = 0°, 2ms = 180° convention, what pulse width commands a servo to 135°?

Answer pulse = 1 + (135/180) × 1 = 1 + 0.75 = 1.75ms.
Intermediate Choose a level-shift divider resistor

A 5V sensor output needs to be brought down to 3.3V for a GPIO input, using a divider with R1 = 10kΩ. What value of R2 is needed?

Answer From Vout = Vin × R2/(R1+R2), rearranged: R2 = Vout×R1/(Vin−Vout) = 3.3×10000/(5−3.3) ≈ 19,412Ω (≈19.4kΩ). In practice, a common off-the-shelf pair like 10kΩ/20kΩ gives 3.33V — close enough to be safe, and widely used for exactly this reason.
Advanced Convert a servo pulse to a duty cycle percentage

A servo signal runs at 50Hz (20ms period). What duty cycle percentage corresponds to a 1ms pulse (the 0° end of travel)?

Answer duty% = 1/20 × 100 = 5%. Confirm it, along with the 1.5ms (7.5%) and 2ms (10%) cases, in the PWM Duty Cycle calculator above.
Advanced Choose a Modbus function code for a Pi-based poll

A Pi running as a Modbus RTU master needs to read 2 holding registers, starting at address 0, from a slave at address 3. Referring back to the Modbus tutorial's function code reference, which function code is needed?

Answer Function code 0x03 (Read Holding Registers). The frame would begin 03 03 00 00 00 02 … — slave address 03, function 03, starting address 0x0000, quantity 2, followed by a CRC-16.
